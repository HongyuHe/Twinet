# 05 — Services and access

Every service the courses depend on is preserved. The implementation changes
from "a container plus a bash generator plus a cron loop" to "a typed component
of the control plane, with the container carrying only the daemon that must
really exist."

## 1. Service inventory

| Service | Today | Twinet |
|---|---|---|
| Connectivity matrix | `matrix` container running `ping.py` in a loop over `destination_ips.txt`, 100 concurrent pings from one container | Distributed probe: each agent pings the AS targets it hosts; results merged by the controller into a matrix document (JSON) + Prometheus metrics. Removes the single-container fan-out bottleneck and the shared-container failure mode. |
| Looking glass | every router runs `looking_glass.sh` under supervisord writing a text file every 30 s, bind-mounted to the host | Agents poll `vtysh -c "show ip bgp json"` on a schedule and push **structured** RIBs to the controller. One collector, no per-container daemon, JSON not text. |
| BGP policy analyzer | Python parsing looking-glass *text* on the web server | Operates on the structured RIB; implements RFC 7908 route-leak detection plus Gao-Rexford violation detection directly against the manifest's declared relationships (which it now actually has access to). |
| DNS | `dns_config.sh` (244 lines) generates bind9 zone files; one bind9 container | Zones generated from the model; served by a small embedded DNS server in the `twinet-dns` container (or CoreDNS with a generated corefile). Reverse zones for every prescribed subnet so traceroute renders `atl.group12`. |
| RPKI | `rpki_config.sh` (275) + `rpki_setup.sh` (369) + `rpki_reload.sh` driving Krill's REST API from bash, plus `sleep 60` | Upstream Krill + Routinator images, provisioned by a typed Go client: create root CA, create one child CA per AS, publish TALs, wire each AS's Routinator. Idempotent, retried, readiness-gated. Per-AS Krill credentials minted with the roster. |
| IXP route servers | `ixp` image with a hand-rolled `docker-start` and generated FRR config | FRR with a generated config implementing community-gated relay (`N:X`); relationships and members come from the manifest. |
| Measurement | `measurement` container with a per-AS interface `groupX` and a default-route-metric trick | Same model (it is good pedagogy — a neutral vantage point), with routes generated rather than derived from a 200-line bash function. |
| Website | Flask app + jinja templates + a separate `PROXY` container | Single Go binary with embedded templates and assets; serves matrix, looking glass, AS connections, BGP analysis, Krill proxy, VPN. No Python, no separate proxy container, no Node build step. |
| VPN | WireGuard containers + `vpnsecret` + a `wg_observer` process **in every router container** | WireGuard endpoint on the front node; peer configs and QR codes generated by the controller; peer status read from the WireGuard interface directly. Removes a per-router background process across ~800 containers (the current README lists its performance as a known bug). |
| History | `history` container git-committing configs hourly + `make_gif.py` needing headless Chrome and gifsicle | Periodic structured snapshots (configs + matrix + RIBs) written to a content-addressed store; the web UI has a time slider. Optionally still `git push`es for the archival workflow. |
| Hijacks | `hijack.sh` + three `question_3_*.sh` scripts doing `docker exec … vtysh` | Declarative `behaviours:` in the manifest (doc 03 §7), applied/reverted idempotently and recorded in the event log. |

Design rule: **a service container runs a daemon that genuinely needs to be in
the topology** (bind/CoreDNS, Krill, Routinator, WireGuard, the FRR route
server). Anything that is really "poll things and render a page" moves into the
control plane where it can be tested, is not duplicated 800 times, and does not
need its own supervisord.

### Replica policy and endpoint availability

Services may declare a typed `replication` policy:

```yaml
services:
  dns:
    kind: builtin.dns
    attach: {template: student_as, router: MSP, iface: dns}
    replication: {mode: per-node}
  measurement:
    kind: builtin.measurement
    attach: {template: student_as, router: HOU, iface: measurement}
    replication: {mode: sharded, shard_size: 16, selector: region}
```

`singleton`, `per-node`, `replicas` (with `replicas: N`), and `sharded` are
supported. Replica IDs, containers, anycast/shard identities, and placement
record keys are deterministic. Placement retains recorded replica locations
when nodes are added; moving them requires `--rebalance` or node-loss
rescheduling. Each attached AS takes a local replica whenever one is available.

An absent policy remains the v1 singleton compatibility behavior, preserving
old manifests and topology hashes. `service_policy_version: v2` is the explicit
default migration for attach-to-every-AS DNS, RTR, matrix, and measurement
services. The scale fixture declares `per-node` directly, reducing its service
cross-links from the old 64% front-node star to zero.

DNS zones and RTR payloads are rendered from one declared state document on
every replica. DNS and RTR clients receive deterministic fallback addresses;
runtime health reconciliation refuses to select an unknown or unhealthy
replica. Matrix/measurement batches execute on the node that hosts their
source/replica and publish bounded collection events for the web collector.

Gateway and web use a multi-endpoint baseline rather than a front-node
dependency:

```yaml
access:
  endpoints: {mode: active-active}
```

`active-active` and `active-standby` support an ordered node list and optional
`vip`; `builtin.web` accepts the same `endpoints:` block under its service
declaration. A VIP is an environment-gated convenience only; `twinet gateway
endpoints` and `twinet web endpoints` always publish deterministic endpoint
lists and conservative health. Set `TWINET_ENABLE_VIP=1` only on an underlay
that has supplied and health-checked the VIP; otherwise the commands mark it
disabled and clients use the endpoint list. Run the same gateway/web service on every
listed node with the shared roster, host key, and scoped mTLS material; failover
therefore does not change group authorization, device placement, or
credentials.

## 2. Access model

Today: one privileged SSH container per group (100 groups = 100 containers),
port `2000+X` on the host, students are root inside, and `goto.sh` computes
target IPs as `158.X.(10i+1)` from a bind-mounted `router_config.txt`.

Twinet uses a **gateway**:

```
student ──ssh group12@host -p 2022──▶ twinet-gateway ──▶ authz(twinet.owner=group12)
                                             │
                                             ├── exec into twinet-cos461-12-ATL   (local)
                                             └── exec via agent on node-2         (remote)
```

- **Identity**: per-group SSH keys and/or passwords minted by
  `twinet gateway roster`. Optional SSH CA so credentials can be rotated/revoked
  without touching `authorized_keys` on a container.
- **Authorization**: the gateway resolves the requested device, checks its
  `twinet.owner` label, and refuses anything else. Isolation no longer depends
  on Docker bridge topology and `iptables/filters.sh`, which answers the
  maintainers' own open question ("Can I get from one ssh proxy to another?").
- **Location transparency**: the gateway proxies the exec to whichever agent
  hosts the device. Students never know or care that their AS lives on node-2.
- **UX preserved**: the interactive shell provides `goto <DEVICE> [router|host|
  container]` with tab-completion generated from the student's own topology,
  plus `save`, `restore`, and `status` — the same verbs as today's
  `goto.sh`/`save_configs.sh`/`restore_configs.sh`, but as gateway built-ins
  instead of generated bash bind-mounted into a container.
- **Compatibility**: `legacy_ports: {enabled: true, base: 2000}` keeps
  `ssh -p 2012 root@host` working, and `scp -O -P 2012 root@host:~/configs_*.tar.gz .`
  continues to work because the gateway serves the save bundle over SFTP.
- **Audit**: every session and every exec is logged (group, device, argv,
  duration) — useful for the "misuse of resources" policy in the assignment,
  which today has no enforcement mechanism.

**Result**: one fewer container per group, real authentication, cluster-wide
access, and the deletion of `configure_ssh.sh` (142 lines), `goto_scripts.sh`
(182), `save_configs.sh` (336), `restore_configs.sh` (192), and
`utils/ssh/portforwarding.sh`.

## 3. Config save / restore

`twinet save --as 12` produces the **legacy directory layout** (so existing
assignment instructions and the GitHub submission flow are unchanged):

```
configs_2025-11-03_14-22-01/
  ATL/router.conf  router.rib.json  router.rib6.json  router.tunnels
  ATL/host.ip      host.route       host.route6
  S1/switch.db     switch.summary
  manifest.json          # NEW: lab, AS, timestamp, twinet version, checksums
```

plus a `.tar.gz`. `twinet restore` validates the manifest, then replays each
device's config transactionally, reporting per-device success — instead of
today's generated bash that pipes a file into `vtysh` and hopes.

Because `manifest.json` records the lab and manifest hash, the grader can
detect a bundle produced against a different topology (a real failure mode when
the class topology is tweaked mid-semester).

## 4. Images

Five images, all built in-repo, multi-arch, published to `hyhe/twinet-*`:

| Image | Contents |
|---|---|
| `twinet-router` | Alpine + FRR (bgpd, ospfd, ospf6d, ldpd, pimd, isisd, staticd) + iproute2 + wireguard-tools + tcpdump. **No sshd, no supervisord, no looking-glass loop, no wg_observer** — exec comes through the agent. |
| `twinet-host` | Alpine + iproute2 + iputils + traceroute + tcpdump + curl + bind-tools. |
| `twinet-switch` | Alpine + Open vSwitch (ovsdb-server + vswitchd), started by a tiny init. |
| `twinet-ixp` | `twinet-router` + generated route-server config. |
| `twinet-svc` | base for DNS / measurement / matrix helper roles. |

Krill and Routinator are consumed as upstream images (pinned by digest) — there
is no value in forking them, and the current fork exists mainly to patch a CLI
and add haproxy, both of which the control plane can handle instead.

Dropping sshd and supervisord from the router image removes two processes ×
~800 containers and eliminates the "containers crash because too many processes
are running" and "proxy containers need regular pruning so they don't hit the
process limit" entries from the current platform's own bug list.
